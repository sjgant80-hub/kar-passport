Your AI's memory stays home. Its passport travels.

Every new AI session starts cold. This tool takes the context your own AI holds and writes a slice of it as one block of plain text: a passport. You paste it into any AI, whether a fresh session, Grok, a colleague's assistant or a local model, and that AI starts up knowing what you are working on. The passport is signed, and it is checked on your side before any model is given it, so a changed or forged one is refused. It comes in three slices: private, shareable and public. Private things never travel in the two that leave.

The passport follows SYMB-FER, the open context-continuity protocol by SYMBEYOND AI LLC (v6.2, MIT). This page runs the same tested code the tool runs, in your browser, offline once loaded. Nothing you type here leaves this tab.

Blueprint: how it is built, organ by organ

1 · The codec

Readers that port SYMBEYOND's v6.2 validator and teslasolar's v3.0 engine line for line, so their verdicts can be compared on every token of the corpus. Writers that build tokens from the template's own lines. A seal: SHA-256 over every line outside §SIG, and an Ed25519 signature carried in §SIG.

src/symbfer.mjs · render.mjs · seal.mjs

2 · The leak gate

Eight kinds of leak, proven first on a planted fixture. It ignores the protocol's own public text, which it has byte for byte, and the signature block. The lists of private names and the operator's names are read on Kar's machine and never stored with the code.

src/leak.mjs

3 · The slicer

Reads Kar's memory index, its topic files, the brain's working memory and the estate index. Writes three slices. Public means only facts that are already public. Shareable means memory's threads with private names turned into reference codes. Full means everything selected, and it stays private.

src/slice.mjs

4 · The hand-back

Checks a returned passport against the one sent, using v6.2's own words, then turns an honest update into a reviewed plan for memory. The plan only adds, keeps the bytes it replaces and can be undone.

src/drift.mjs

5 · The boot

Verifies first and only then asks a model. A refused passport makes zero model calls. A sealed question set and its answer key, read from the passport, measure what a cold model knows after reading it.

src/boot.mjs

6 · The sealed rules

One judge turns each claim's measured facts into HELD or FAILED by the rule written in claims.json before any code. A verdict's wording is chosen by the verdict, never by a second copy of its condition.

src/judge.mjs

7 · The time case

What re-typing a brief by hand costs a team, from the lines of memory Kar's STATE passport carries, a measured typing speed and the reader's own figures. Every outside figure is read from a sourced basis, byte for byte.

src/timecase.mjs · vendor/basis/basis.json · data/typing-basis.json

8 · Team notes

Your team's own notes, in the layout Claude Code's memory folder uses, into the same three slices: full (every note), shareable (every note but those about a person) and public (only the notes you mark public). Every value that leaves passes the leak gate first, and what a session handed back comes back in.

src/notes.mjs · node kar/passport.mjs notes

Security, data protection and compliance

  • Data minimisation (UK GDPR Article 5(1)(c)). Each target gets only its slice. The public slice holds only facts that are already public, and personal data becomes reference codes whose lookup stays on your machine.
  • Hosted AI is a processor. Pasting a passport into a hosted AI sends its contents to that provider; SYMBEYOND's own security notes say the same. Send hosted AIs only the public or shareable slice, and keep the full slice for your own sessions.
  • Integrity. SHA-256 over every line outside the seal, plus an Ed25519 signature. The check (the command line's verify, this page, and the tool's own boot) refuses a token that was changed, or signed by a key you have not pinned: your own, and each colleague's you pinned with trust. It runs on your side: a chat AI cannot check a signature itself, so you check before you paste, and in checks your sent copy before it reads what came back.
  • No server, no telemetry. This page and the tool run locally. Signing keys never leave the device that made them. The page loads only its own files from this site and makes no other request, and your browser enforces that: the page's content security policy allows scripts, styles, requests and workers from this site only, with no inline script and no inline style, so not even an injected script could send what you type anywhere. Its offline cache holds only those files, all of them from the first visit.
  • No third-party packages. The tool has no package dependencies (its package.json lists none). The few files it carries from elsewhere (SYMBEYOND's template, validator and generator, teslasolar's engine, two fall-kit modules and the cost basis) are pinned by SHA-256. CI re-fetches each one from its source at its commit and compares it on every push.
  • The signing key. Its seed is one file on your machine, in ~/.kar-passport/. On Linux and macOS it is written readable by your user only (mode 600); on Windows it sits in your user profile, which Windows opens only to you and the machine's administrators. It is never in the code, a passport, or any page. Your checks trust only the public half you pin. The key this page makes for you lives in the tab's memory and is gone when you close it.
  • Audit. Every hand-back is written to a log that only grows, with the before-bytes kept so it can be undone.
  • Sub-processors. None of ours. The tool runs on your machines and calls no service. The only processor is the AI you choose to paste a passport into. This demonstration page is served by GitHub Pages, and what you type into it stays in the tab.

Security questions, answered

  • Where is the drift check enforced? On your side, when a passport comes back, against the copy you sent. The receiving AI needs nothing and is trusted with nothing: whatever it returns is checked line by line before any of it reaches your memory.
  • What about a leak the gate was not taught? Two layers. The public slice is built only from facts that are already public: your public pages, their public descriptions, and the business facts you publish. A private note is never a candidate, so nothing private is there to be missed. The gate then checks every line for eight kinds of leak, each proven on planted examples. The shareable slice draws on memory's threads, so for that one the gate is the line of defence: send it only to people you would show those threads.
  • Can a model infer what is not in the passport? It can guess, but it cannot learn private facts from a slice that does not hold them. In the cold boots, the model was asked for an email address, a private repository and a person's name that were withheld. None of them appeared in any answer.
  • What if a session does work the protocol does not cover? The session records it where the protocol says: in the new §CURRENT·REALITY and an appended §SESSION·LOG block. Any change anywhere else is drift and is refused, however the session did its work and whatever tools it used.
  • Can a passport or a hand-back carry instructions into our AI? A passport is text, and nothing in it is run. Your tools read only passports signed by a key you pinned, so a stranger's text is refused before a model sees it, and every passport carries SYMB-FER's own instruction to treat it as provided context, not established fact. A hand-back is text an AI wrote. It reaches your memory only through a plan the command line prints line by line, only in the parts the protocol lets a session change (the session log, milestones, lessons, resolved items, closed threads and the current reality), and only when the memory's owner applies it, with undo kept. Read a plan as you would read any AI's output before you keep it.
  • Which cryptography signs and checks a passport? Ed25519 signing and verifying run in the platform's own WebCrypto, in Node and in the browser, not in code of ours. SHA-256 is a small pure function from the estate's fall-kit, pinned by its hash, so the page and the command line hash the same bytes the same way. A test checks it against Node's own SHA-256, from OpenSSL, on every push: the standard test messages of FIPS 180-2, every length from 0 to 300 bytes, random bytes, and every committed passport (src/sha256.test.mjs). The Proof's tampering claim (P6) is that check at work: every changed copy refused.
  • What if a signing key is lost or exposed? Replace it. Move the old seed file aside, run node kar/passport.mjs key to make a new one, and pin its public half in place of the old one. Every passport the old key sealed is then refused by your checks, and you make fresh ones at the next session end. Each colleague who pinned your old key runs node kar/passport.mjs untrust <name> and pins the new one; until they do, they refuse your new passports and still accept the old key's. Nothing else depends on the key.
  • What if a session's work holds sensitive data? The hand-back is merged into your private memory, which never travels. The next public or shareable passport is sliced and gated again from scratch.
  • Regulation. The passport is a document you control. When you paste it into a hosted AI, that provider processes it under your agreement with them. Choose the slice for the recipient as you would for any document.

How you make passports on your own machine

What your notes look like. A folder of Markdown files, one per topic. Each opens with a short header between two lines of three hyphens, giving its name, description and type. The types are project (work in hand), feedback (a rule to keep), reference (a term or a pointer) and user (about a person). An index, MEMORY.md, links them in the order that matters. This is the layout Claude Code's memory folder uses, so a team that works in Claude Code already has one. Two optional lines are this tool's own: public: true in a header marks a note as already public, and a body line that starts Next: is a next action.

  1. Get the tool: git clone https://github.com/sjgant80-hub/kar-passport, then cd kar-passport (needs Node.js 22 or later).
  2. Write ~/.kar-passport/config.json, for example { "memory": "/path/to/your/notes", "about": { "name": "Your Name", "org": "Your Company Ltd", "site": "https://your.site" }, "private": ["names that must never leave"] }. Only memory is required. On Windows, write each backslash of the folder's path as a forward slash: in JSON a backslash starts an escape, and the command refuses a file it cannot read with the reason, not a crash. The name comes from about and from git's user.name. The leak gate keeps your surname out of the shareable and public slices and your first name out of the public one, and turns every name under private into a reference code whose lookup stays on your machine.
  3. Run node kar/passport.mjs key > keys/kar.json once. It makes your signing key and pins its public half, the only key your checks then trust. The seed stays in ~/.kar-passport/. The clone arrives with Kar's public key in that file, and this replaces it with yours. In Windows PowerShell the > writes the file with a byte-order mark; the tool reads it either way.
  4. At the end of a session, run node kar/passport.mjs notes. It makes the full, shareable and public slices, each in five shapes, all sealed, in ~/.kar-passport/tokens/. A shareable or public one that the leak gate flags is not written. Check any of them with node kar/passport.mjs verify <file>.
  5. Paste a slice into the AI you are using. The full slice is for your own sessions. Hosted AIs get the public or shareable slice.
  6. To check a colleague's passport before you paste it, pin their key once. They send you the file their step 3 wrote (their keys/kar.json: a public key, safe to send), and you run node kar/passport.mjs trust <their file> <a name>. From then on verify accepts their passports and says whose key sealed each one; your own still verify. node kar/passport.mjs untrust <the name> removes it again, and their passports are refused. A file that is not a key, a name already used, your own key or a name that is not a plain file name is refused, and nothing changes.
  7. When the session hands back an updated passport, run node kar/passport.mjs in <sent> <returned> to see the plan, then apply it (and undo if you change your mind). The next notes run carries the session's work.

Steps 1 to 4 and 7 are what The proof's claim N1 runs, as written, on every push: the receipt says how it went. Step 6, the handover, is what claim R1 runs, with three people: the receipt says how it went. On Windows too: on every push, CI types steps 2 to 4 in Windows PowerShell on GitHub's Windows runner, checks that its > wrote the byte-order mark, verifies every passport with the key it pinned, and re-derives N1 and R1 there. Kar's own memory has more parts than a notes folder (a working memory and a digest), so Kar runs node kar/passport.mjs generate instead of notes. Everything else is the same.

Tested with: a cold local qwen2.5:7b (two boots, scored in The proof) and a fresh Claude session (the hand-back loop). Any model that reads plain text can take it. A live Grok run waits on its API key. Sizes: Kar's v6.2 passports, as their records give them; the NANO, CORE and STATE tiers are at most their limit, their limit and their limit characters. One memory per team or project gives each its own passports and its own key.

White paper: a checked passport for AI context

The problem

Language models are stateless between sessions. Vendor memory features fill part of the gap, but the memory belongs to the vendor and stays inside one product. A team that uses several AIs, or that changes AI, keeps rebuilding the same brief.

The protocol

SYMB-FER (SYMBEYOND AI LLC; cite as SYMB-FER, SYMBEYOND AI LLC, 2026) is an open, plain-text format for carrying context across sessions: identity, posture, current reality, threads, a session log, milestones and lessons, in a strict section order with its own drift rules. Version 6.2 has its required sections, and SYMBEYOND publishes a validator for it. Kar's passport builds every token to v6.2, and SYMBEYOND's own validator passes it.

What the passport adds

A seal, checked on the sender's side before a model is given the passport, and on the owner's side before a hand-back is read. Slices, so each target gets only what it should. A drift check that enforces the protocol's own rules on a returned token. And a hand-back that merges a session's work into memory without dropping anything, in a way that can be undone.

Can it plug into our existing systems?

Yes, through plain files and one command. Notes go in; passports come out as text files; a check is one command that exits zero or not. Anything that can run a command or move a file can use it: a scheduler, a CI job, a document store or an intranet page. There is no server to host and no API to keep alive.

How are problems or disputes resolved?

Technically, the record decides: every passport is signed, every hand-back is logged with what changed, and any merge can be undone. Commercially, under each deployment's agreement with AI Native Solutions.

Does the AI I paste it into need to understand SYMB-FER?

No. The passport explains itself in its first sections, including a symbol legend and a reading order. Any model that reads plain text can use it.

Can I paste the full slice into a hosted AI?

What stops someone editing a passport and passing it off as yours?

The signature. Change one character anywhere and the SHA-256 no longer matches. Sign it with another key and that key is not on the trust list. Either way the check refuses it before any model reads it. The check is yours to run: node kar/passport.mjs verify, against the public key you pinned (this page runs the same check on Kar's passports). A chat AI cannot check a signature itself.

Why are some answers in the passport "unscored" or "not recorded"?

Because the memory holds no value for them, and nothing is invented. The six-question thread score, for example, is the operator's judgement.

What does it take to run, and to keep running?

No licence fee: it is MIT-licensed. It runs on the machines you already have: Node.js for the command line, and any modern browser for this page. Setting up is one config file that says where your notes live, plus one command to make a key. After that, one command at the end of a session makes the passport, and one at the start checks it. Support terms, if you want any, are agreed per deployment.

What happens when a model misreads a passport?

A passport is provided context, not established fact: its own §SAFETY·INTERPRETATION section says so. The operator stays the authority, and SYMB-FER's §DRIFT·CHECK gives the operator the call on whether to continue or redirect. A correction goes into the next session, the session log keeps the record, and a model cannot quietly rewrite what it was given, because a returned passport that changes anything outside the parts the protocol lets a session change is refused.

What if the AI cannot take a long passport?

Use a tier. The same slice also comes as SYMBEYOND's NANO, CORE and STATE tokens (at most their limit, their limit and their limit characters), each sealed and checked the same way.

Several people, one company?

Each person or team keeps its own memory, its own key and its own reference lookup. A shareable passport carries project context with private names replaced by codes. Trust is by key: you choose whose keys your checks accept. Your own is pinned in keys/kar.json; each colleague's you add with node kar/passport.mjs trust <their key file> <name> and remove with untrust <name>, so when someone leaves, removing their key refuses every passport it sealed. verify says whose key sealed each passport.

Are there limits on slices or versions?

No. A passport is a text file. Each session end makes a new one, and the hand-over log in memory only grows.

Does this replace AI memory?

No. Memory holds; the passport transfers. You need both: a home to keep context in, and a passport to carry a slice of it to another session.
